# Task: Fix Race Condition in Cache Invalidation

## Bug Report

Under load, users occasionally see stale product prices after an admin updates them. The cache returns the old price for 1-5 seconds after the update, even though the TTL is set to 60 seconds. This happens more frequently during peak traffic.

## Current Implementation

```python
class ProductCache:
    def __init__(self):
        self._cache: dict[str, tuple[Any, float]] = {}  # key -> (value, expiry)

    def get(self, key: str) -> Any | None:
        if key in self._cache:
            value, expiry = self._cache[key]
            if time.time() < expiry:
                return value
            del self._cache[key]  # expired
        return None

    def set(self, key: str, value: Any, ttl: int = 60) -> None:
        self._cache[key] = (value, time.time() + ttl)

    def invalidate(self, key: str) -> None:
        # BUG: between check and delete, another thread can set a new value
        if key in self._cache:
            del self._cache[key]
```

## File Location

- Source: `app/cache/product_cache.py`
- Tests: `tests/test_product_cache.py`

## Root Cause

The `invalidate` method is not atomic. Between `if key in self._cache` and `del self._cache[key]`, a concurrent `set()` call can insert a new value. The `invalidate` then deletes the fresh value, but a third concurrent `get()` may have already read the stale entry before `invalidate` ran.

## What to Test

Write a test that spawns concurrent set/invalidate/get operations and asserts the cache never returns a stale value after invalidation completes.
